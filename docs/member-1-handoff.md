# Member 1 frontend handoff

This checklist is for the existing static frontend in `client/`. It recommends changes for Member 1; it does not claim those changes are implemented. Keep the same-origin `/api` URLs so the UI works both when Express serves it directly and when NGINX serves it in Docker or Kubernetes.

## Do first

| Priority | Frontend change | Current evidence | Done when |
| --- | --- | --- | --- |
| 1 | Render API and `localStorage` values safely. Build text nodes with `textContent` or an equivalent safe renderer; validate image URLs and use event listeners instead of interpolating IDs into inline `onclick`/`onchange`. | `restaurants.js`, `menu.js`, `cart.js`, and `orders.js` insert names, descriptions, customer details, image URLs, and IDs into `innerHTML`. `app.js` also puts toast messages into `innerHTML`. | A restaurant name, cart item, order field, or error message containing HTML is displayed as text and cannot execute script. |
| 1 | Rework the order-history and status UI around an access-controlled API. Do not present every customer's name, phone, address, and status controls to any visitor. Coordinate the required authentication or limited order-lookup contract with the backend owner; hide the status-simulation controls from ordinary customers. | `orders.js` fetches the global `/api/orders` list and exposes unauthenticated status-update controls. | Ordinary users can see only their own permitted order details and cannot change status; demo/admin controls are clearly isolated. Frontend hiding alone is not authorization—the backend must enforce it. |
| 1 | Make checkout display the server's authoritative order total and validation errors. Send item IDs and quantities, not a trusted price or total; keep the cart until the order is confirmed. Handle an unavailable item or changed price with a clear refresh/review action. | `cart.js` calculates fees from `localStorage` prices and submits `price` and `totalAmount`; the server currently trusts those values. | A tampered cart cannot set the price shown as paid; a rejected order does not clear the cart or leave the submit button disabled. Backend validation must be updated alongside the UI. |
| 2 | Validate persisted cart shape and quantities before rendering or checkout. Treat `localStorage` as untrusted, cap quantities to a reasonable positive integer, and handle stale/deleted menu items. | `app.js` accepts any parsed value from `localStorage`, then assumes it is an array of valid items. | Invalid or outdated cart entries do not crash the page or produce `NaN` totals; the customer sees a useful recovery message. |
| 2 | Make search match what the home page promises. Either search menu items as well as restaurant names/cuisines/locations, or change the “Search food or restaurants” text and food-category links to match the current restaurant-only filter. | The home page links to `restaurants.html?search=...`, but `restaurants.js` filters only restaurant fields. | Searching a food name such as a menu item returns a meaningful result, or the UI no longer promises food search. |
| 2 | Fix loading, empty, and error states for the deployed topology. Remove messages that tell users to start a server on port `5000`; the browser uses the frontend's same-origin `/api` proxy. Preserve the search/cart context during retry. | Error states in `restaurants.js` and `orders.js` name backend port `5000`, which is not the public URL in Docker/Kubernetes. | API outage and 404 states give a useful retry path without exposing internal port assumptions. |
| 3 | Improve keyboard and screen-reader behavior. Maintain `aria-expanded` on the mobile menu, announce cart/toast updates, give the success overlay dialog semantics and focus management, and label quantity/status controls. | The mobile toggle only changes CSS; the success overlay and dynamic controls have no dialog/live-region behavior. | Navigation, cart, checkout, and confirmation can be completed by keyboard and announced meaningfully by a screen reader. |
| 3 | Add frontend behavior tests and a responsive smoke-test checklist. Cover search/filter, cart persistence and totals, checkout success/failure, order visibility, and injected-text handling. | `npm test` currently covers one API restaurant-list request, not browser behavior. | Tests run in CI without network image/font dependencies; manual checks cover narrow mobile and desktop widths. |

## Coordination and scope

The backend must enforce order access, status permissions, and authoritative pricing. Frontend changes alone cannot secure those operations. Agree on updated response shapes with the backend owner before changing `client/js/cart.js` or `client/js/orders.js`, and update both sides and tests together. Do not replace `/api` with a hard-coded `localhost:5000` URL; the NGINX proxy and Kubernetes Service depend on same-origin routing.

No external food dataset is needed for these UI changes: the repository already has six sample restaurants and 28 menu items. Use synthetic values for security and UI tests, not real customer details. Commit each logical change separately, then run `npm run check`, `npm test`, and browser smoke tests before handing it to the pipeline.
